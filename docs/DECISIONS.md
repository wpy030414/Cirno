## ADR-101：技术栈选 C# + WinUI 3
- 日期：2026-10-22
- 状态：已采纳
- 背景：需要一个真正的原生 Windows 壳，承载虚拟化时间线、自定义标题栏、Mica、任务栏集成。
- 考虑过的方案：C# + WinUI 3；C++/WinRT；WPF；Avalonia。
- 决策：C# 13 / .NET 10 + WinUI 3（Windows App SDK 2.x），MVVM 用 CommunityToolkit.Mvvm。
- 为什么选这个：Fluent 2 控件与材质是一等公民；JSON/SQLite/进程管理生态成熟；迭代速度远高于 C++/WinRT。
- 为什么不选其他：C++/WinRT 控制力更强但开发成本翻倍；WPF 拿不到 Mica 与新控件；Avalonia 不是 Windows 原生观感。
- 后果：绑定 Windows 11（Win10 降级为纯色）；WinUI 3 不支持 Native AOT，发布走裁剪 + 自包含。
- 何时重新审视：WinUI 出现无法绕过的阻塞缺陷，或需要跨平台。

## ADR-102：直接实现后端 stdio 协议，不引入 sidecar
- 日期：2026-10-22
- 状态：已采纳
- 背景：Claude Code 与 Codex 都提供基于 stdio 的程序化协议，官方 SDK 是 TypeScript/Python。
- 考虑过的方案：用官方 SDK 跑一个 Node sidecar 通过本地 IPC 转接；在 C# 里直接实现协议。
- 决策：C# 直接读写 JSONL / JSON-RPC。
- 为什么选这个：少一层运行时与打包负担；协议本身是行分隔 JSON，解析成本低；审批应答要求低延迟，直连最稳。
- 为什么不选其他：sidecar 多一个 Node 分发与版本兼容问题，且跨进程转发会放大审批延迟。
- 后果：需要自己维护协议兼容（靠真实抓包夹具测试兜底）。
- 何时重新审视：协议复杂度显著上升（例如引入大量双向回调）或官方提供 .NET SDK。

## ADR-103：主链路不引入 WebView2
- 日期：2026-10-22
- 状态：已采纳
- 背景：「远超终端与 Electron 的原生体验」是产品卖点，消息渲染是最容易退回 Web 技术的地方。
- 考虑过的方案：WebView2 渲染 Markdown/代码/diff；原生 XAML 渲染。
- 决策：Markdown 用 Markdig 解析成 AST，再映射为 XAML（RichTextBlock/TextBlock + 原生语法高亮）；代码与 diff 用原生控件。
- 为什么选这个：选择、复制、滚动、无障碍、键盘操作与系统一致；没有第二套渲染引擎的启动与内存开销。
- 为什么不选其他：WebView2 会带回 DOM/CSS 的性能曲线与视觉割裂，等于重做一遍 Electron。
- 后果：Markdown 边角语法（Mermaid、内嵌 HTML、数学公式）需要单独定策略，首版明确「不支持并给出占位」。
- 何时重新审视：出现必须渲染交互式图表/HTML 的刚需，届时以单实例隔离面板引入，而非全量替换。

## ADR-104：自建 SQLite 归一化存储，而非直接读后端历史
- 日期：2026-10-22
- 状态：已采纳
- 背景：两个后端的历史格式不同（本地 JSONL 文件 vs 服务端 thread），但侧边栏、搜索、跨后端统一体验需要同一套索引。
- 考虑过的方案：每次启动解析后端历史；自建 SQLite 存归一化条目。
- 决策：SQLite（WAL）+ 全文索引保存会话元数据、条目、审批记录；后端历史作为恢复真相源。
- 为什么选这个：侧边栏与搜索是毫秒级需求；跨后端字段可统一；后端格式变化不影响本地 schema。
- 为什么不选其他：直读历史在会话多、消息多时启动不可接受，且两种格式要写两套 UI 数据源。
- 后果：存在冗余存储，需要在「恢复会话」时做一次导入与去重。
- 何时重新审视：后端提供稳定的跨客户端会话查询协议且性能足够。

## ADR-105：provider 是进程级属性，不做运行期切换
- 日期：2026-10-22
- 状态：已采纳
- 背景：每个会话要能选不同 provider/model。
- 考虑过的方案：运行时切换 provider；把 provider 绑定到进程启动参数。
- 决策：provider 决定子进程的环境（Claude）或配置目录（Codex）；切换 provider 等于重启对应的后端进程，必要时以 `resume` 续接。
- 为什么选这个：两个后端的真实实现就是进程/配置级的，没有运行期 API；硬造会让状态不可信。
- 为什么不选其他：伪造运行期切换会导致「界面显示 A、实际跑 B」。
- 后果：切换 provider 有一次短暂重连；UI 需要如实提示。
- 何时重新审视：后端提供 per-session provider 覆盖参数。

## ADR-106：主题管线保留为构建期工具，新增 XAML 发射器
- 日期：2026-10-22
- 状态：已采纳
- 背景：旧项目已验证「插画取色 → 46 token → 明暗双套」的管线，但消费端从 CSS 变量变成 XAML 资源。
- 考虑过的方案：把取色移植到 C#；保留 Node 管线并新增发射器。
- 决策：`tools/theme`（Node/TS）保留取色与 token 生成，新增 `emit-xaml`：产出 `Theme.xaml`、位图资产与主题注册表。
- 为什么选这个：算法与对比度规则已经跑通，重写没有收益；构建期运行不进入分发产物。
- 为什么不选其他：移植到 C# 只会得到一份等价但未经打磨的实现。
- 后果：仓库同时存在 Node（构建期）与 .NET（运行期）两套工具链。
- 何时重新审视：主题需要在应用内即时取色（如用户拖入自己的图）。

## ADR-107：默认主题零图片，「大肥鱼」作为可选主题
- 日期：2026-10-22
- 状态：已采纳
- 背景：插画主题好看但会干扰长期阅读；纯 Fluent 才是「原生体验」的基线。
- 考虑过的方案：默认带插画；默认纯 Fluent + 可选插画主题。
- 决策：默认主题不加载任何图片，只用 Fluent 资源与 Mica；「大肥鱼」主题由构建期产物提供，用户手动切换。
- 为什么选这个：默认状态应当是最耐看、最不影响可读性、启动最快的；个性是可选项而非强制。
- 为什么不选其他：把插画当默认会让所有人先承受背景干扰与额外体积。
- 后果：需要一套运行期主题切换机制（换资源字典 + 换装饰层），不能靠重启。
- 何时重新审视：用户希望首次启动即带主题，或主题数量增长到需要预览图管理。

## ADR-108：删除 Electron 皮肤引擎
- 日期：2026-10-22
- 状态：已采纳（对应旧决策 D-001~D-026 全部作废）
- 背景：Cirno 自己就是宿主，不再需要给别人的 app 打补丁；补丁策略受上游升级、CSP、DOM 变化制约。
- 考虑过的方案：保留旧代码作为参考/回归夹具；直接删除。
- 决策：删除 `skins/qwenwork`、`skins/opencode`、`skins/codex`、asar 补丁与 CDP 注入代码、相关 specs 与注入模块；历史保留在 git 中。
- 为什么选这个：不可用的代码会持续误导后续 Agent 与读者，维护成本远大于参考价值。
- 为什么不选其他：git 历史已完整保留，需要时随时可取。
- 后果：仓库从「多 target 皮肤 monorepo」变成「单应用 + 构建期主题工具」。
- 何时重新审视：不再（该路线已被产品方向排除）。

## ADR-109：未识别的后端条目降级展示
- 日期：2026-10-22
- 状态：已采纳
- 背景：两个后端都在快速演进，新增 item 类型是常态。
- 考虑过的方案：严格 schema 校验；宽容解析 + 未知条目降级。
- 决策：未知条目渲染为「原始数据」卡片并保留原始载荷；未知字段忽略。
- 为什么选这个：一次上游新增不应导致界面崩溃或内容丢失。
- 为什么不选其他：严格校验会让应用在后端小版本升级时直接不可用。
- 后果：需要一套调试视图让用户/作者查看原始事件。
- 何时重新审视：协议进入稳定期并提供版本协商。

## ADR-110：MSI 分发，缺依赖时引导安装
- 日期：2026-10-22
- 状态：已采纳
- 背景：目标用户要在干净机器上装上就能跑，且不希望手动装运行时。
- 考虑过的方案：免安装压缩包；MSIX；MSI + 前置检查。
- 决策：以 MSI 为交付物，采用自包含发布；若检测到缺失的运行时依赖，引导用户安装（详见 `specs/module-packaging.md`）。
- 为什么选这个：MSI 是 Windows 上最通用、可静默、可企业分发的形式；自包含把「缺 .NET」这类问题消灭在打包阶段。
- 为什么不选其他：免安装包无卸载/升级体验；MSIX 需要签名与证书信任链，早期迭代成本高。
- 后果：安装体积较大；无包标识，部分 WinRT API（如通知、跳转列表）需走无包标识路径。
- 何时重新审视：需要商店分发或自动更新时，补一条 MSIX 通道。

## ADR-111：Claude 审批走 stdio 控制协议，宿主必须先发 initialize
- 日期：2026-10-22
- 状态：已采纳
- 背景：M1 需要「允许 / 拒绝 / 中断」，必须在宿主里接管工具授权。
- 考虑过的方案：`PreToolUse` hook 每次 fork 一个进程回传决策；stdio 控制协议（`can_use_tool`）。
- 决策：走 stdio 控制协议，启动参数固定带 `--permission-prompt-tool stdio`，并在进程就绪后立即发 `initialize` 控制请求。
- 为什么选这个：零额外进程、决策延迟在毫秒级、同一通道还能中断与切权限模式；hook 方案每次工具调用都要起进程并经过命名管道往返。
- 为什么不选其他：hook 的权限决策属于旁路，与 CLI 内建授权流程并行，容易出现两套真相互相矛盾。
- 后果：两个开关缺一不可（`--permission-prompt-tool stdio` + `initialize`）。实测缺任一项时工具被静默拒绝，且**没有超时**，表现为「模型说没权限」而不是报错。该结论写进 spec 与 AGENTS，防止后续改动踩回坑里。
- 何时重新审视：官方提供 .NET SDK，或该隐藏参数被移除。

## ADR-112：流式增量只做打字效果，权威内容取全量消息
- 日期：2026-10-22
- 状态：已采纳
- 背景：`--include-partial-messages` 会同时给出 `stream_event` 增量与 `assistant` 全量消息，两者表达同一内容。
- 考虑过的方案：只信增量拼出完整文本；只信全量、放弃打字效果；增量驱动显示、全量做幂等覆盖。
- 决策：条目 id 用 `blk:<message_id>:<index>`；增量按此 id 追加，全量到达后按同 id 覆盖。
- 为什么选这个：增量让首字延迟可见，全量保证最终内容与后端一致（不缺字、不重复）。
- 为什么不选其他：只信增量在后端重连、重发或多网关改写时会缺字；只信全量则长回答要等十几秒才出字。
- 后果：必须保证 id 对齐；实测部分第三方网关的 `stream_event` 不带 `type` 字段，此时增量被忽略、只剩余全量路径——宁可没有打字动画，也不能显示错内容。
- 何时重新审视：后端提供稳定的增量序号与校验。

## ADR-113：claude 可执行文件优先解析原生 exe，不用命令行 shim
- 日期：2026-10-22
- 状态：已采纳
- 背景：Windows 上 `claude` 常见形态是批处理 shim（npm 或包装器生成），而 `Process.Start` 无法在重定向 stdio 的同时直接启动它。
- 考虑过的方案：一律经 shell 启动；优先找原生 `claude.exe`，找不到才退回 shell。
- 决策：解析顺序为 `CIRNO_CLAUDE_PATH` → PATH 中的 `claude.exe` → npm 全局布局下的 `bin/claude.exe` → PATH 中的 `.cmd/.bat`（经系统 shell 的 `/d /s /c` 形式）。
- 为什么选这个：原生 exe 没有 shell 介入，参数不必过 shell 转义（含引号的 JSON 参数尤其致命），进程树与退出码也更干净。
- 为什么不选其他：全部走 shell 会让每个参数都过一层引号规则，容易出现「看起来启动成功、实际参数被截断」。
- 后果：需要维护两条启动路径；shim 分支只作兜底，且不保证复杂参数。
- 何时重新审视：Claude Code 在 Windows 上只提供批处理分发。

## ADR-114：会话 id 由宿主生成且必须是标准 UUID
- 日期：2026-10-22
- 状态：已采纳
- 背景：本地记录要与后端会话一一对应，才能做「重启 → 恢复」。
- 考虑过的方案：让后端生成 id 再回写；宿主先生成、以本地 id 作为会话主键。
- 决策：宿主生成标准 UUID（连字符形式）作为会话 id，并在启动参数里显式传给后端；后端回报的 id 另存为 `backend_session_id`。
- 为什么选这个：创建即可落库（不需要等后端就绪），本地 id 稳定，恢复时用后端 id 续接；两者解耦，后端换了也不影响本地记录。
- 为什么不选其他：等后端给 id 意味着「会话创建」这段时间没有主键，UI 与存储都要处理空 id。
- 后果：id 格式受后端约束——**必须是带连字符的 UUID**。M2 第一版用了无连字符格式，Claude 直接以 `Invalid session ID` 退出，整轮失败。
- 何时重新审视：有后端要求非 UUID 的会话标识时，改为「本地 id + 后端 id 分离，本地 id 不参与后端调用」。

## ADR-115：并发上限 4，超出排队而不是拒绝
- 日期：2026-10-22
- 状态：已采纳
- 背景：多会话并行是本产品卖点，但每个 Claude 会话都是一个独立进程与一次真实 API 调用。
- 考虑过的方案：不限制；限制并拒绝；限制并排队。
- 决策：同时运行 4 个，其余进入 `Queued` 状态并显示「等待中」，有空位自动继续。
- 为什么选这个：4 个已经覆盖「人眼能同时关注的会话数」，再高的并发不会提升体验，只会放大上下文成本与进程开销；排队比报错更符合直觉。
- 为什么不选其他：不限制会让用户随手开十几个会话把机器和额度打满；直接拒绝则需要用户自己重试。
- 后果：编排层需要一个信号量，并额外暴露 `Queued` 状态；审批等待期间**仍占用**并发位（它确实在运行）。
- 何时重新审视：并发主要来自后台长任务而非人机交互时，改为按「活跃轮次」而非「会话」计数。

## ADR-116：任务栏集成挂在窗口子类化上，等 TaskbarButtonCreated
- 日期：2026-10-22
- 状态：已采纳
- 背景：`ITaskbarList3` 要求在任务栏按钮已创建之后调用，否则 `AddTab` / `SetProgressState` 静默失败或直接无效。
- 考虑过的方案：在 `Window.Activated` 里初始化；用 `SetWindowSubclass` 挂接窗口消息，收到 `TaskbarButtonCreated` 再初始化。
- 决策：子类化窗口，收到消息初始化；同时附带一次「立即初始化」的兜底（消息在挂接前已经发过的情况）。
- 为什么选这个：`Activated` 的时机早于任务栏按钮创建，是社区里最常见的「进度条不显示」原因；消息驱动才是官方约束。
- 为什么不选其他：轮询 `FindWindow` 找任务栏窗口再试，既不可靠也无必要。
- 后果：需要维护子类化回调，并在窗口销毁时清理；托盘回调也复用了这条消息通道。
- 何时重新审视：WinAppSDK 提供官方的任务栏 API（目前没有）。

## ADR-117：子进程用 Job Object 托管，接受启动窗口期
- 日期：2026-10-22
- 状态：已采纳
- 背景：应用崩溃时不会走「优雅退出」，子进程可能残留并继续消耗额度。
- 考虑过的方案：只在会话销毁时杀进程；用 Job Object（`KILL_ON_JOB_CLOSE`）托管。
- 决策：后端进程一启动就按 PID 加入同一个 Job；应用退出/崩溃时关闭作业句柄即回收整棵进程树。
- 为什么选这个：内核级兜底，不依赖应用主动清理；对适配器只增加一个 PID 回调，不引入平台依赖。
- 为什么不选其他：`Process.Start` 无法以挂起方式创建进程（除非自写 `CreateProcess` 参数），因此存在「进程已启动、尚未加入作业」的极小窗口；这个窗口用主动清理无法消除，只能靠尽快加入来缩小。
- 后果：加入失败（例如进程已在别的作业里）只记录不阻塞；该窗口期在 ADR 与 spec 里明确写出。
- 何时重新审视：需要严格零窗口时，改为自实现 `CreateProcessW(CREATE_SUSPENDED)` + 先入作业再恢复。

## ADR-118：托盘菜单用 Win32 原生弹出菜单
- 日期：2026-10-22
- 状态：已采纳
- 背景：托盘图标点击时应用窗口通常不在前台，甚至不可见。
- 考虑过的方案：弹出 XAML `MenuFlyout`；用 `TrackPopupMenuEx` 弹原生菜单。
- 决策：原生菜单，命令通过菜单 ID 回到 App。
- 为什么选这个：不依赖 XAML 视觉树的焦点与布局，也不需要窗口可见；行为与系统托盘图标一致。
- 为什么不选其他：`MenuFlyout` 需要 `XamlRoot`，窗口隐藏时会抛错或显示在错误位置。
- 后果：菜单文案只能纯文本（没有图标/子菜单样式），且需要处理「先 SetForegroundWindow 再弹菜单、弹完 PostMessage(WM_NULL)」这两个老坑。
- 何时重新审视：托盘菜单需要富交互（自定义渲染、预览）时。

## ADR-119：流式期间正文走纯文本快路径，结束后再解析 Markdown
- 日期：2026-10-22
- 状态：已采纳
- 背景：合帧提交意味着正文每秒被改写约 30 次；如果每次都重建 Markdown 块树，长回答会把 UI 线程吃满。
- 考虑过的方案：每帧重新解析 Markdown；流式期间只更新纯文本，流结束后解析一次；增量式解析（只解析新追加的块）。
- 决策：流式期间 `MessageBody` 只维护一个 `TextBlock`；`IsStreaming` 变 false 时再解析 Markdown 重建。
- 为什么选这个：实现成本最低、收益最大；流式期间用户看的是「字在长」，格式晚 0.3 秒出现无感。
- 为什么不选其他：增量解析要维护块级游标与未闭合围栏状态，复杂度远高于收益。
- 后果：流式期间代码块没有高亮与边框，结束后统一出现；`IsStreaming` 必须由宿主在条目完成时置 false，否则永远不回落到富渲染。
- 何时重新审视：需要「逐字高亮代码」这类实时格式需求时。

## ADR-120：文件变更默认展开，且不把成功回执混进 diff
- 日期：2026-10-22
- 状态：已采纳
- 背景：`FileChange` 条目的价值就在 diff 本身；默认折叠等于什么都没呈现。
- 考虑过的方案：全部折叠（统一交互）；文件变更默认展开；只显示摘要+按钮打开详情。
- 决策：`FileChange` 默认展开，其余工具条目默认折叠；成功回执丢弃，错误回执保留。
- 为什么选这个：审阅改动的动作发生在阅读时，不该多一次点击；成功回执（"has been updated successfully"）会变成 diff 里的无意义上下文行。
- 为什么不选其他：全部折叠让「原生 diff」这个卖点看不见；另开详情面板在 M6 前成本过高。
- 后果：一次改动很大的 diff 会占满视口，需要滚动；超过 600 行时截断并提示。
- 何时重新审视：单条 diff 经常超过一屏时，改为「摘要 + 可展开全文」。

## ADR-121：MSI 按用户安装（免管理员），工具链固定 WiX 5
- 日期：2026-10-22
- 状态：已采纳
- 背景：目标用户是个人开发者，装一个本地工具不应该先要管理员权限；同时打包工具要能免费、可脚本化。
- 考虑过的方案：per-machine 装到 Program Files（需提权）；per-user 装到 `%LOCALAPPDATA%\Programs\Cirno`。
- 决策：per-user + WiX 5.0.2。
- 为什么选这个：per-user 安装无 UAC、无残留的机器级注册表、卸载更干净；WiX 5 是最后一个不需要接受 OSMF 商业授权的版本（v7 会直接拒绝构建）。
- 为什么不选其他：per-machine 对个人工具过重；换用别的打包器（Inno/NSIS）会失去 MSI 的企业分发与静默安装语义。
- 后果：不能写 `HKLM`，也没有包标识；换成 WiX 6/7 前必须先处理授权。
- 何时重新审视：需要机器级部署或商店分发时。

## ADR-122：VC++ 运行库随包 app-local 部署，不做安装期检测
- 日期：2026-10-22
- 状态：已采纳（取代 ADR-110 中的检测+引导方案）
- 背景：自包含的 .NET 不带 `vcruntime140.dll` / `msvcp140.dll`，而 WinAppSDK 的原生 DLL 依赖它们。
- 考虑过的方案：安装时读注册表检测 → 缺失就引导安装 redist；把编译器自带的可再分发 DLL 直接放进应用目录。
- 决策：app-local 拷贝（`Microsoft.VC143.CRT\*.dll`，10 个文件约 2MB）。
- 为什么选这个：微软允许随应用再分发；「缺依赖」直接不存在，比任何引导流程都可靠；MSI 内无自定义动作、无二次安装、可离线。
- 为什么不选其他：检测 + 引导要维护注册表判断、静默模式分支、重启码 3010 处理，而收益只是省 2MB。
- 后果：运行库版本跟构建机绑定，安全更新需要重新发版；`/qn` 场景不再有依赖失败分支。
- 何时重新审视：微软提供官方 NuGet 形式的 CRT 运行库时。

## ADR-123：发布产物必须自带 `<AssemblyName>.pri`
- 日期：2026-10-22
- 状态：已采纳
- 背景：MSI 装完后应用一启动就崩在 `Microsoft.UI.Xaml.dll`（0xC000027B / E_FAIL）。
- 考虑过的方案：改用 MSIX/打包应用；在 publish 后补一条拷贝 PRI 的目标。
- 决策：csproj 增加 `EnsurePriInPublishDirectory`（`AfterTargets="Publish"`），把 `$(TargetDir)$(AssemblyName).pri` 拷进 `$(PublishDir)`。
- 为什么选这个：`dotnet publish` 对非打包 WinUI 应用不会带上 PRI，缺少它 XAML 资源（含 BAML 与 `Themes/` 内容）无法解析；这是构建链的缺陷，不值得为此改分发形态。
- 为什么不选其他：MSIX 需要签名与证书信任链，与 ADR-121 的免管理员取向冲突。
- 后果：构建脚本之外还要记住这条；已在 csproj 注释与 packaging spec 里写明「发布必须包含 PRI」。
- 何时重新审视：Windows App SDK 修复该 publish 行为后。

## ADR-124：协议解析与进程管理分离，协议形状由夹具承载
- 日期：2026-10-22
- 状态：已采纳
- 背景：Claude 的 stream-json 协议解析原本写在 `ClaudeSession` 里，和进程/管道/控制通道缠在一起。协议一旦变化，只能靠真实调用来验证，回归全靠人肉。
- 考虑过的方案：保持原样，靠真实 claude CLI 手测；引入官方 SDK；把解析抽成纯状态机。
- 决策：抽出 `ClaudeEventParser`（输入一行 JSON → 产出归一化事件），`ClaudeSession` 只管进程与管道；协议样本落在 `tests/fixtures/*.jsonl`，由测试回放。
- 为什么选这个：协议形状有了单一事实来源；测试不依赖 claude 是否安装、不依赖网络、跑得飞快；进程管理出问题时能明确区分是「协议变了」还是「管道断了」。
- 为什么不选其他：官方 SDK 是 TypeScript/Python，等于把协议复杂度搬到另一门语言（违反 ADR-102）；继续手测则每次协议变更都要重跑真实会话，成本高且不稳定。
- 后果：适配器多一层间接；协议新增字段要同步改解析器与夹具（这正是想要的：改一处必有一处红）。
- 何时重新审视：协议复杂度显著上升、需要维护状态机快照时。

## ADR-125：端到端测试用假 CLI 驱动，不依赖真实后端
- 日期：2026-10-22
- 状态：已采纳
- 背景：协议夹具只能验证「解析」，验证不了「进程真的起来了、控制请求真的回了、审批真的往返了」。
- 考虑过的方案：跑真实 claude CLI（要装、要账号、要网络）；只测纯函数；写一个假 CLI。
- 决策：`tests/Cirno.FakeClaude` 是个真可执行文件，按环境变量给定的剧本回放预录 stream-json，并自动应答宿主的 `control_request`；测试用 `.cmd` 包装它，通过 `CIRNO_CLAUDE_PATH` 注入。
- 为什么选这个：能覆盖进程启动、管道读写、初始化握手、审批往返、中断这些真实链路，同时完全离线、可重复、无副作用。
- 为什么不选其他：真实 CLI 让测试依赖外部状态，CI 上必然不稳定；只测纯函数则进程与管道这段代码完全没有护栏。
- 后果：假 CLI 与真实 CLI 的行为差异可能掩盖问题，因此夹具必须来自真实抓包；假 CLI 也成了协议演进的试验田。
- 何时重新审视：真实 CLI 提供了稳定的可编程测试接口时。

## ADR-126：单实例用命名互斥体 + 命名管道，启动意图以文本协议转交
- 日期：2026-10-22
- 状态：已采纳
- 背景：跳转列表点「新建会话」会启动第二个进程；此时不应再开一个窗口，而应让已有实例新建会话。
- 考虑过的方案：WinUI 自带的 `AppInstance`（WinAppSDK 有，但 API 面窄）；自己实现；干脆允许多实例。
- 决策：命名互斥体 `Local\Cirno.SingleInstance` 判主从；命名管道传「启动意图」（`new` / `cwd` / `prompt` / `front`，以 `\u001f` 分隔的 key=value 文本）。
- 为什么选这个：互斥体判主从零依赖、可靠；文本协议不需要跨进程序列化依赖，调试时能直接看到管道里传了什么。
- 为什么不选其他：`AppInstance` 的重定向参数只支持字符串、且行为随版本变；允许多实例会让用户看到几个同样的托盘图标与任务栏分组。
- 后果：管道名与互斥体名是隐式契约，改名会让新旧版本无法互认；文本协议不含版本号，未来加字段只能追加。
- 何时重新审视：需要传结构化复杂数据（如批量会话恢复）时。

## ADR-127：跳转列表的 COM 声明以本机 Windows SDK 头文件为准
- 日期：2026-10-22
- 状态：已采纳
- 背景：实现跳转列表时先后踩了三个坑：`ICustomDestinationList` 的 IID 网上流传的值是错的；vtable 方法顺序写错导致 `AddUserTasks` 打到了 `AddObject` 的槽位；`IObjectCollection` 的 `AddObject`/`AddFromArray` 顺序写反直接段错误。
- 考虑过的方案：照抄网络上的示例代码；用 `Marshal.QueryInterface` 探针逐个试；核对 SDK 头文件。
- 决策：所有 COM 接口声明逐字对照 `C:/Program Files (x86)\Windows Kits\10\Include\<ver>\um\shobjidl_core.h` 与 `objectarray.h`；IID 一律以头文件为准。
- 为什么选这个：COM 是按 vtable 槽位调用的，声明顺序错一位就是静默的内存破坏（表现为随机段错误，不报错）；SDK 头文件是唯一权威来源。
- 为什么不选其他：网络示例错的地方往往是「看起来对但顺序不对」，照抄必踩；探针法只能验证 IID，验证不了顺序。
- 后果：每个 COM 接口都要手工核对，代价高但一次性；已在 `JumpListService` 的类注释里固化这三条教训。
- 何时重新审视：不再新增 COM 交互时。

## ADR-128：万条消息性能以基准数字固化，不靠主观感受
- 日期：2026-10-22
- 状态：已采纳
- 背景：M5 的出口条件写了「万条消息会话滚动不掉帧」，但一直没有数字。评审只能凭「感觉还行」。
- 考虑过的方案：写个一次性脚本测一下；用测试把预算固化；只测存储层。
- 决策：两层。存储层用 `tools/perf` 与 `tests/Cirno.Core.Tests`（写入 < 2000ms、读取 < 1000ms 为硬预算）；界面层用 `Cirno.exe --perf N` 在真实窗口里测还原/绑定/滚动/内存，报告落 JSON。
- 为什么选这个：数字进版本库才能当护栏——`AppendItem` 曾把序号改成每条查 `MAX(seq)`（O(n²)），基准能立刻发现；界面层的 `BindMs` 才是用户真正感知的成本。
- 为什么不选其他：一次性脚本测完就忘，下次回退无人察觉；只测存储层会漏掉「逐条 Add 导致绑定列表重排上万次」这类界面侧问题。
- 后果：CI 里跑测试需要有稳定的磁盘性能，阈值不能卡太死；界面层基准是人工触发的（`--perf`），不进 CI。
- 何时重新审视：拿到可复现的 CI 机器后，把界面层基准也纳入流水线。

## ADR-129：升级前用应用自己的单实例管道关闭运行中的实例
- 日期：2026-10-22
- 状态：已采纳
- 背景：MSI 覆盖安装时，若旧版本还在运行，文件被占用会导致安装失败或要求重启。
- 考虑过的方案：靠 MSI 内置的 Files-in-Use 检测（可能安排重启）；只用 `util:CloseApplication`（发 WM_CLOSE）；让安装器调用应用的关闭命令。
- 决策：双保险。`util:CloseApplication` 负责通用的进程关闭与提示；再由 CustomAction 调用已装好的 `Cirno.exe --shutdown`，走 ADR-126 的管道让主实例主动收尾（回退挂起审批、关子进程、落 WAL checkpoint）。后者用注册表标记 `ShutdownSupported` 保护，旧版不认识该参数就不会被误调用。
- 为什么选这个：Cirno 常驻托盘，WM_CLOSE 不一定能可靠退出；应用自己的收尾路径知道该怎么干净地停。
- 为什么不选其他：只用 WM_CLOSE 在托盘常驻场景下不可靠；只用自定义动作则旧版会把它当普通启动而弹窗。
- 后果：安装包多了两个自定义动作与一个注册表开关；`--shutdown` 成了对外契约的一部分。
- 何时重新审视：应用不再常驻托盘，或 Windows 提供了更标准的应用关闭协商机制时。

## ADR-130：历史还原一次性提交给绑定列表
- 日期：2026-10-22
- 状态：已采纳
- 背景：会话历史可能有上万条。原实现逐条 `ObservableCollection.Add`，绑定列表会收到上万次 `CollectionChanged`，每次都可能触发一次布局。
- 考虑过的方案：逐条加但节流；分页/虚拟化数据源；一次性提交。
- 决策：`BulkObservableCollection<T>` 提供 `AddRange`，把批量追加压成一次 Reset 通知；`SessionViewModel.LoadHistory` 改用它。
- 为什么选这个：`ListView` 本身已做容器虚拟化，瓶颈不在「画多少个」，而在「通知多少次」；一次 Reset 让绑定方整体重建一次即可。
- 为什么不选其他：节流会让还原过程持续占用 UI 线程；引入分页数据源是更大的架构改动，收益与当前规模不匹配。
- 后果：Reset 通知会让绑定方丢弃原有滚动位置与选择状态——对「打开历史会话」这个场景恰好是对的。
- 何时重新审视：需要在还原过程中保持增量状态时。

## ADR-131：界面视觉体系对齐 Fluent 2 令牌层，依赖版本对齐 Ceobe
- 日期：2026-10-22
- 状态：已采纳
- 背景：界面此前是单文件 `MainWindow.xaml`，标题栏手写、间距与字号散落（7/10/13.5/12.5/11.5），
  材质没有纯色回退；观感与同为 WinUI 3 的 Ceobe 差距明显。
- 考虑过的方案：只调局部样式；引入一套设计令牌层并重排主壳；换成第三方 UI 框架。
- 决策：
  1. 新增 `Styles/Spacing|Typography|Controls|Content.xaml` 四套令牌：4px 间距网格、官方字阶、
     统一卡片/图标按钮/对话框/列表行样式；页面只允许从令牌取值。
  2. 主壳改用 `TitleBar` 控件 + `NavigationView`（会话导航、PaneHeader/PaneFooter 动作），
     右侧工作区为「会话头 + 时间线 + Composer 卡片 + 状态条」。
  3. 材质加纯色回退：`MicaController.IsSupported()` 时启用 `MicaBackdrop(BaseAlt)` 并隐藏回退层，
     否则保留 `ApplicationPageBackgroundThemeBrush` 纯色层。
  4. 依赖版本对齐 Ceobe：`Microsoft.WindowsAppSDK 2.5.1`、`CommunityToolkit.Mvvm 8.4.2`；
     不显式钉 `Microsoft.Windows.SDK.BuildTools`（避免 NU1605 降级）。
- 为什么选这个：视觉问题来自「没有约束」而不是「控件不够花哨」；令牌层把一致性变成编译期约定，
  同时不改变任何会话/协议语义。
- 为什么不选其他：换第三方框架会引入远程依赖与渲染层分叉，违背「原生 Fluent 2」定位；
  只调局部样式无法解决数值散落与标题栏 caption 避让。
- 后果（踩过的坑）：
  - `NavigationView.MenuItemsSource` 只能由 XAML 赋值，代码赋值会命中 WinUI 原生层崩溃（0xC0000005）；
    会话集合用 `ObservableCollection<object>` 镜像 + `x:Bind` 单向绑定。
  - 行模板不要给 `SessionViewModel` 加 `x:DataType`：XAML 类型生成器会沿公开属性构造 `SessionRecord`
    的激活器，撞上 `required` 成员而编译失败；行内改用经典 `Binding`。
  - 材质不可用时必须有纯色层，否则深色下透明根元素会让文字落在白底上不可读。
- 何时重新审视：需要跟随系统主题（第三态）、或改为多页面导航时。

## ADR-132：会话列表以后端本地历史目录为权威源
- 日期：2026-10-25
- 状态：已采纳
- 背景：会话列表此前只来自 Cirno 自己的 SQLite 库，终端里直接用 CLI 开的会话对 Cirno 不可见；
  ADR-104 预留的「恢复会话时一次导入与去重」缺口从未实现。用户要求以本地 Claude Code 目录为权威源。
  实测（CLI 2.1.301）目录布局为 `~/.claude/projects/<munged-cwd>/<session-uuid>.jsonl`（`CLAUDE_CONFIG_DIR` 可重定向根），
  Cirno 经 `--session-id` 指定的 UUID 落盘同名，两种来源同处一个命名空间。
- 考虑过的方案：每次启动全量解析目录（ADR-104 已否决）；目录元数据扫描作列表权威 + 首次打开惰性导入 SQLite；放弃本地库直读渲染。
- 决策：
  1. Abstractions 新增 `IAgentHistorySource`（`ListSessions` 元数据扫描 / `ReadTranscript` 全量解析 /
     `TryDeleteTranscript` 移入回收站），`IAgentBackend.History` 默认 null，Claude 适配器实现之。
  2. `GetSessionsAsync` 以目录扫描为准：每文件只窥读前 64KB（cwd / 首时间戳 / 首条人类消息 / 末条 ai-title 或 summary），
     `LastActiveAt` 用文件 mtime；SQLite 只补充运行期字段（model/title）与 pending 会话
     （`backend_session_id` 为空、还没有转录文件的）。库里有、目录里没有的会话不再列出（条目留库，文件恢复后自然重现）。
  3. 时间线惰性导入：`LoadItemsAsync` 在库无条目、或文件 mtime 晚于库 `updated_at` 时，
     解析转录并 `ReplaceItems` 整体重建（单事务 DELETE+INSERT）。活会话（进程在跑）不重导入，避免与 live 写入竞态。
  4. 标题优先级：ai-title > summary > 首条用户消息（折行、截 42 字，与既有规则一致）。
  5. 删除会话 = 转录移入 Windows 回收站 + 清本地库；回收站失败则中止删除（库保留，可重试）。
- 为什么选这个：元数据扫描把 ADR-104 否决的理由（启动全量解析、双格式 UI 数据源）拆掉了——
  列表只需文件名/mtime/64KB 窥读，时间线仍走既有 SQLite 渲染管线；「权威源」落在「什么会话存在」这一个问题上是用户要的语义。
- 为什么不选其他：直读渲染放弃本地库会丢掉 ADR-128 的性能护栏与既有还原路径；
  全量解析已被 ADR-104 以性能理由否决，且 1MB+ 转录文件逐个解析会拖慢冷启动。
- 后果（踩过的坑）：
  - live 落库的 user 条目 id（`user:<guid:n>`）与转录行 `uuid` 不同源，按 item_id 去重不可靠——
    导入幂等必须建立在 `ReplaceItems` 整体重建上，不能靠 `AppendItems` 的 id 巧合。
  - 转录 user 行 content 既可能是字符串也可能是 `array[text]`；人类输入判定须综合 `isMeta`/`isSidechain`/`origin.kind`，
    否则会把命令回显与宿主注入的提醒当作用户消息。
  - 回收站 API 不能用 `Microsoft.VisualBasic.FileIO`：.NET 10 共享框架里没有它（在 WindowsDesktop 框架），
    适配器是纯 `net10.0` 不能拖 WinForms——改用 `SHFileOperationW` P/Invoke（字段序对照 SDK `shellapi.h`，专用 STA 线程）。
  - pending 会话必须从库保留进列表，否则「新建但未发送」的会话会在侧栏凭空消失。
- 何时重新审视：Claude Code 提供稳定的跨客户端会话查询协议时（回到 ADR-104 的重审条件）；
  或 Codex 后端接入时（其 `thread/list` 官方 API 与文件目录语义需要重新对齐）。

## ADR-133：新建会话改为草稿态，首条消息才落库入列
- 日期：2026-10-25
- 状态：已采纳
- 背景：点「+」立刻调用 `SessionOrchestrator.CreateSession` 写 SQLite 并插入侧栏，用户还没发任何消息就先得到一个「新会话」条目；
  工作目录由侧栏的文件夹按钮在创建瞬间决定，输入前没有调整机会。侧栏因此出现大量空壳，与「列表只反映真实会话」的直觉相悖。
- 考虑过的方案：先落库但侧栏隐藏到首条消息；纯 UI 草稿，首条消息时才创建会话。
- 决策：
  1. `MainViewModel` 增加草稿态：`DraftWorkingDirectory` + `BeginDraft()`，`ActiveSession` 置空；草稿不写库、不占侧栏。
  2. `MainWindow.SendAsync` 在无活动会话时先 `CreateSession(DraftWorkingDirectory)` 再发送——发送是会话的诞生时刻。
  3. 工作目录在会话创建后锁定：Composer 的选择控件只存在于草稿态，会话开始后不再出现。
  4. 收窄 ADR-132 的 pending 保留规则：`backend_session_id` 为空且**条目数为 0** 的会话不再列出（旧版本遗留的空壳）。
  5. `RestoreAsync` 不再无条件选中第一项：用户已在草稿态时保留草稿，不抢选择。
- 为什么选这个：草稿是纯视图状态，最符合「还没发生的事不写进账本」；也避免 ADR-132 的 pending 语义把幽灵会话带回列表。
- 为什么不选其他：先落库再隐藏会污染数据库，重启后仍要靠过滤规则维持「不可见」，且删除/切换/退出都要额外处理幽灵记录。
- 后果：
  - 旧版本点「+」留下的零条目 pending 在升级后从侧栏消失（条目与标题不受影响）。
  - 托盘、跳转列表、Ctrl+N 的「新建会话」统一变成「进入草稿」，带 prompt 的启动意图在发送时才落库。
  - 新建会话跳过首次历史扫描（`MarkHistoryLoaded`），避免发送瞬间在 UI 线程遍历历史目录。
- 何时重新审视：需要「会话模板」或「预创建后排队」时（草稿可能要持久化）。

## ADR-134：界面移除模型选择与状态/路径行，右上角改为打开工作目录
- 日期：2026-10-25
- 状态：已采纳
- 背景：右上角模型选择器只影响「下一个」会话（模型是进程级属性），与当前会话无关，概念成本高于收益；
  top-bar 同时显示状态、模型、用量与工作目录三行，把视觉重心从内容挪到了元信息；侧栏另有「在目录中新建会话」按钮，与 Composer 的目录选择重叠。
- 考虑过的方案：保留选择器但降级为详情面板；彻底移除，模型只由配置/启动参数决定。
- 决策：
  1. 删除模型选择器；`--model` 仍是新建会话指定模型的唯一入口（开发/自检）。
  2. 主内容区 top-bar 只显示标题；状态交给侧栏状态点与底部聚合状态条。
  3. 原选择器位置改为文件夹图标：在资源管理器中打开当前会话（或草稿）的工作目录。
  4. 侧栏顶部只保留「+」；删除中心空状态的「新建会话」按钮。
  5. `SessionHost` 内的 `{Binding}` 一律带 `FallbackValue`：草稿态 DataContext 为空时，
     Stop 按钮不得按 `Visibility` 默认值露出，标题应显示「新会话」。
- 为什么选这个：界面只保留「会话列表 + 标题 + 时间线 + 输入」四件事；模型与用量是诊断信息，不是日常决策点。
- 为什么不选其他：保留选择器再加解释文案，只会把复杂度留在最重要的位置；放到详情面板等于另行设计一个页面，超出当前阶段。
- 后果：模型不再在界面可见（后端回报仍落库，可用 `--restore-check` 或 `sqlite` 查）；
  README/PRD 中「会话级模型可见/可选」的表述需要同步修订。M3 恢复 provider 选择时再重新设计呈现。
- 何时重新审视：Codex 后端接入、需要会话级模型切换时。

## ADR-135：历史导入清洗斜杠命令回显（标题与时间线）
- 日期：2026-10-25
- 状态：已采纳
- 背景：侧栏出现标题 `<command-name>/clear</command-name>`，时间线也会把命令回显当用户气泡导入。
  实测 CLI 2.1.301 的 `/clear` 行 `type=user`、**无 `origin`、无 `isMeta`**，content 为
  `<command-name>…</command-name><command-message>…</command-message><command-args>…</command-args>`（带缩进）；
  自定义命令（如 `/xat:upload-repo`）的 `origin.kind` 反而是 `human`。ADR-132 只按 `isMeta/isSidechain/origin` 判定人类输入，前提被真实数据推翻。
- 考虑过的方案：只靠 origin 判定；只在标题归一化时清洗；读取层统一剥离机器块。
- 决策：
  1. 新增 `ClaudeUserText.Sanitize`：成对剥离 `<command-name>`、`<command-message>`、`<command-args>`、
     `<local-command-caveat>`、`<local-command-stdout>`、`<system-reminder>`，Trim 后为空即视为机器行。
  2. 读取路径共用：历史标题提取（`ClaudeHistorySource`）与转录导入（`ClaudeEventParser.TryReadHumanPrompt`）。
     用户实际发送的文本（`ClaudeSession.SendUserMessageAsync`）绝不经过清洗。
  3. `IAgentHistorySource` 增加默认方法 `NormalizeStoredTitle`，列表回退到库内旧标题时由适配器清洗。
  4. `ReadTranscript` 用全量解析出的首条人类消息补标题（覆盖 64KB 窥读窗口外的首条消息）；
     `LoadItemsAsync` 导入后触发 `SessionChanged`，侧栏无需重启即可刷新。
  5. 本地库加 `PRAGMA user_version` 一次性缓存迁移：清掉有转录文件会话的条目与标题，
     下次打开按新规则重导入（SQLite 是可重建缓存，ADR-132）。
- 为什么选这个：机器块的形态由适配器决定，清洗必须留在 Claude 适配器内；标题与时间线共用同一判定，避免两处漂移。
- 为什么不选其他：只改标题会留下时间线气泡；在 `SessionStore` 或 Core 里清洗会把后端专有格式泄漏进存储层/编排层。
- 后果：
  - 人类正文若完整引用这些标签会被剥离（可接受；正文里成对出现的情形极少）。
  - 升级后首次启动会清空历史会话的本地条目，点开时重新导入；pending（无转录）会话不受影响。
- 何时重新审视：Claude Code 改变命令回显格式，或提供结构化的用户消息类型时。

## ADR-136：主界面第二轮体验修正（默认目录、阅读位置、宽度、思考预览、Composer 焦点、图标）
- 日期：2026-10-25
- 状态：已采纳
- 背景：第一轮简化后仍有七处体验问题：新会话默认目录不是家目录；进入会话停在时间线顶部；
  窗口拉宽后正文被拉到整屏；思考条目折叠时不显示任何文字；底部常驻「N 个会话」状态条占空间；
  Composer 的 TextBox 在获得焦点时叠出白底与蓝色下划线；应用图标仍是旧图。
- 决策：
  1. 新会话默认工作目录固定为用户主目录（`~`），不再沿用最近会话；Composer 在发送前仍可选择。
  2. 进入会话或历史批量导入（`Reset`）后强制滚到时间线底部；内容到达时仍按「距底部 240px 内才跟随」的规则。
  3. 内容区最大宽度取 `CirnoContentMaxWidth`（960），窗口更宽时居中留白；宽度在 `SizeChanged` 里夹取。
  4. 时间线条目的折叠摘要优先 Detail，没有则回退 Text——思考条目只有 Text，此前摘要永远为空。
  5. 删除主内容区底部的全局状态条；聚合状态继续供给任务栏/托盘（`SummaryChanged` 仍在）。
  6. Composer 的 TextBox 覆盖 `TextControlBackground*` / `TextControlBorder*` / 聚焦厚度等主题资源为透明与 0，
     使输入框与卡片同面，彻底去掉焦点白底与蓝色下划线。
  7. 应用图标重绘为暖墨底、奶油色帆船与陶土色 Claude 星芒：多尺寸 ICO（16–256，PNG 条目），
     同时用于 exe、标题栏与任务栏。
- 为什么选这个：这些都是「阅读与输入」路径上的摩擦，修复集中在视图层，不动会话与协议语义。
- 后果：思考条目摘要是纯文本首行（不解析 Markdown）；状态条移除后，单会话细节只在侧栏状态点体现。
- 何时重新审视：需要展示会话用量/模型等元信息时（应另设详情面板，而不是恢复状态行）。
